# Primo Bugs

| Page | Issue | Fix Required | Status |
|---|---|---|---|
| Store Profile | Categories card showed hardcoded chips (Menswear, Military Heritage, Outerwear) + a non-functional "+ Add Category" button | Remove Add Category button; fetch L1 categories from `GET /boutique/categories/tree` (same hook AddProduct uses) and show only categories with `product_count > 0` | Fixed |
| Sidebar | Store cover photo not rendering at top of sidebar | `coverPhoto` was built from raw `cover_photo_url` without the `IMG_BASE` prefix, so the image URL never resolved | Fixed |
| ViewProfile / Sidebar | Logged-in user's own account photo (ViewProfile.jsx) is the same asset as the boutique's Founder Card photo (`founder_photo_url` / `POST /boutique/profile/founder-photo`) — uploading one overwrites the other | Backend delivered a role-aware `my_photo_url` field on `GET /boutique/profile` (no new endpoint — returns founder-*.jpg when called as owner, staff-*.jpg when called as staff; upload still goes through the existing `POST /boutique/profile/founder-photo`). `ViewProfile.jsx` and `Sidebar.jsx`'s bottom user avatar now read `my_photo_url` instead of `founder_photo_url`; `StoreProfile.jsx`'s public Founder Card correctly left untouched on `founder_photo_url`. Also wired up the login response's `staff: {id, name, role, photo_url, preferred_locale}` object: `lib/auth.js` now persists it (`setStaff`/`getStaff`/`clearStaff`, cleared alongside the token on logout), `Login.jsx` stores it on successful login, and `Sidebar.jsx`'s bottom widget now shows the boutique's Founder Card name/title only for the owner — a non-owner staff member sees their own name and role (from the login snapshot) instead | Fixed |
| ViewProfile / Sidebar | Uploading a photo in ViewProfile.jsx only updated that page's own local state — the Sidebar's bottom avatar (fetched once on its own mount) kept showing the old photo until a full page refresh | `Sidebar.jsx` had no way to know ViewProfile had just uploaded a new photo. No new file: `ViewProfile.jsx` fires a `window.dispatchEvent(new CustomEvent('primo:my-photo-updated', {detail:url}))` after a successful upload; `Sidebar.jsx` listens for that same event (literal event name in both files, no cross-import) and updates its own `myPhotoUrl` state, so the sidebar avatar updates immediately with no refresh needed | Fixed |
| Edit Product | Category path (e.g. Men's > Accessories > Shoes) shows correctly before Save Changes, but resets to "Choose..." with the top-level list when the product is reopened | Root cause: delimiter mismatch — backend returns `category_path` as `"Women's / Dresses / Mini"` (` / `) but the frontend everywhere split/joined on `" > "`, so the saved path never matched a tree node and silently fell back to empty. Fixed all 7 spots to use `" / "`: `AddProduct.jsx` (save payload ×3), `CategorySelector.jsx` (restore parse), `Products.jsx` (Print Tag category parse), `POS.jsx` (category tab extraction + filter ×2) | Fixed |
| Edit/Add Product | "Selected Category" breadcrumb separators (`>` between Men's / Suits / Two-Piece) were nearly invisible and vertically misaligned with the crumb text | `.cat-bc-sep` used `color:var(--mist)` (near-background beige) instead of `var(--stone)` used by the identical chevron icon elsewhere in the same component; also lacked `display:inline-flex;align-items:center` for proper centering. Fixed in `App.css`: recolored to `--stone`, added flex centering + `line-height:1` on `.cat-bc-sep`/new `.cat-bc-chevron`/`.cat-bc-crumb` | Fixed |
| Edit Product (Shoes categories) | Custom size rows (e.g. UK 7/EURO 40/10cm) added via Edit Sizes never populate Variants & Stock (stays "One Size"), and vanish entirely on reopen | Two bugs in `VariantTable.jsx`: (1) Shoes schema's first column key is `uk` not `size`, but rows were passed to `onRowsChange`/`sizes` state un-normalized, so every downstream `.size` filter (Variants & Stock, save payload) silently dropped them — no variants ever got saved; (2) the restore effect permanently locked itself into a degraded single-column fallback the moment it ran before category had finished resolving, blocking the correct multi-column (UK/EURO/cm) restore from ever running once category loaded. Fixed both: added a `withSize()` normalizer applied at every `onRowsChange` call site, and removed the premature seed-and-lock so the schema-aware restore always wins once category resolves | Fixed |
| Edit Product (any category) | Newly added sizes still don't persist after Save Changes for products that already had stock data or zero existing variants | Two more bugs in `AddProduct.jsx`, both in the variants-save path: (1) `buildVariantsPayload` picked `stockData` outright over `sizes` whenever `stockData` was non-empty — but `stockData` is only refreshed on manual qty/toggle edits or the Variants & Stock card's own Save button, so it goes stale the instant a size is added elsewhere, silently dropping the new size from what gets saved; (2) `saveChanges()` (the page's Save Changes button) additionally gated the entire `variants` field on the product's *old* variant count (`variants.length > 0 ? buildVariantsPayload(...) : undefined`), so a product with zero existing variants sent `variants: undefined` — dropping the field from the PUT entirely regardless of fix (1). Fixed: `buildVariantsPayload` now always uses `sizes` as the row list and only pulls quantities from `stockData` where they still match; `saveChanges()` now calls `buildVariantsPayload` unconditionally, matching the pattern already used by the other PUT call site in the same file | Fixed |
| Edit Product (Shoes categories) | UK values in the Sizes card persist correctly after reopen, but the EURO / To Fit Foot Length (cm) columns render blank | `buildSizeChartPayload` (`VariantTable.jsx`) excluded the size chart's identifying column via `cols.filter(c => c.key !== 'size')` — for Shoes the identifying column's key is `uk`, not `size`, so it was never excluded and the saved `columns` metadata came out wrong (`[UK, EURO, cm]` instead of `[EURO, cm]`). Fixed to exclude the first column by position (`cols.slice(1)`) instead of by literal string match | Fixed, superseded by next row's root cause |
| Edit Product (Shoes categories) | Confirmed via a live `GET /boutique/products/:id` response: `size_chart` saved as `null` even after retyping EURO/cm and clicking Save Sizes | Real root cause: EURO/cm cells render as always-editable inputs regardless of "Edit Sizes" mode (`col.editable`), but the plain "Save Sizes" button shown outside of edit mode (`VariantTable.jsx`) only called `onRowsChange` — it never called `notifySizeChart`, so any measurement typed directly into those boxes was never pushed to `AddProduct.jsx`'s `sizeChart` state, leaving `size_chart: null` on save. Only the editing-mode Save button called `notifySizeChart`. Fixed: the plain "Save Sizes" button now also calls `notifySizeChart(activeCols, rows)`, matching `saveEditing()`. Also cleaned up a cosmetic issue found along the way: column keys slugified from labels like "To Fit Foot Length (cm)" produced ugly double/trailing underscores (`to_fit_foot_length__cm_`) — now collapsed/trimmed properly | Fixed (frontend) |
| Edit Product (Shoes categories) | Backend does not persist `size_chart` — verified via actual network payload that the frontend sends a correct, well-formed, non-null `size_chart` object (`{unit:'cm', columns:[{key:'euro',...},{key:'to_fit_foot_length_cm',...}], rows:[{size:'7', euro:'8', to_fit_foot_length_cm:''},...]}`) on `PUT /boutique/products/:id`, but the very next `GET` on that product returns `size_chart: null` | Backend fixed — `size_chart` now round-trips correctly | Fixed |
| Edit Product (Shoes categories) | After the backend persistence fix, EURO/cm now restore correctly on reopen, but the first (UK) column renders blank | Saved chart rows always store the identifying value under the canonical key `"size"` (by design, for a stable API shape across all schemas), but the live render (`activeCols`, from the current schema) expects it under that schema's own first-column key (`uk` for Shoes) — the restore code in `VariantTable.jsx` hardcoded a reconstructed column literally keyed `"size"`, which the Shoes table never reads from, so the UK cell always came up empty. Fixed to remap the saved `size` value onto the live schema's actual first-column key when rebuilding rows from `initialSizeChart` | Fixed |
| Edit Product (Colour Variants) | Removing existing colours (e.g. Camel, Burgundy) and adding a new one (Mustard) shows correctly before save, but after Save Changes and reopening, the removed colours reappear alongside the new one | Verified via actual `PUT /boutique/products/:id` request payload that the frontend sends exactly the intended `variants` list (3 Mustard rows, zero Camel/Burgundy entries) — confirmed correct, no frontend staleness bug. Backend's PUT handler was only upserting variants present in the payload and never deleting existing rows missing from it. Backend fixed — retested removing a colour (Mustard) and adding a new one (Stone) in the same save; reopened product correctly shows only the intended colours | Fixed (backend) |
| Edit Product (Variants & Stock) | Updated stock quantity for an existing colour (Default) resets to its old value after Save Changes + reopen, while a newly added colour's stock persists correctly | Verified via actual `PUT /boutique/products/:id` request payload across several rounds that the frontend always sent the correct `stock_qty` and the correct existing `id` for the Default variant — no frontend bug. Same root cause as the colour-deletion issue above (backend upsert/reconciliation logic) — confirmed resolved by the same backend fix; retested updating an existing colour's stock alongside removing/adding other colours in one save, and the update now persists correctly on reopen | Fixed (backend) |
