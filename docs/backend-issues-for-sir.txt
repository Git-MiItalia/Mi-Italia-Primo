--- 1. Plan feature text is not translatable, and is duplicated -------------

  GET /boutique/subscription/plans returns each plan's feature list as finished
  sentences:

      "features": [ { "text": "2 email campaigns/month", "included": true }, … ]

  The portal prints `text` exactly as sent, because there is no key to look up.
  So this list is the one part of the portal that does not follow the
  translation bundle: an Italian boutique reads the plan cards in whatever
  language the rows were written in, and reloading translations changes
  nothing on that card.

  This caught us out in a real way. We edited the plan wording in primo5.json
  ("2 email campaigns/month" → 100), you loaded it, the bundle updated, and the
  Subscription page still showed the old numbers — because the words on that
  card never came from the bundle.

  The duplication behind it: the same nine-or-so feature lines exist twice, as
  bundle keys (sub.setup.feat_*, used by the plan chooser at
  /subscription-setup) and as your `features[].text`. Editing either one leaves
  the other stale, and the two screens then disagree about what a plan
  includes.

    NEEDED, and the smaller of the two options: send a key per feature
    alongside the text, e.g. { "key": "feat_2_campaigns", "text": "…" }. We
    look up the key and fall back to your text when we do not have it, the
    wording lives in the bundle like everything else, and we can delete our
    hardcoded copy so there is one source.

    Numbers that differ per plan (500 contacts, 2 campaigns, 25 renders) are
    better sent as interpolation values than baked into the sentence —
    { "key": "feat_campaigns", "count": 2 } — otherwise every limit change is
    a translation change in eight languages.


--- 2. The plan cards advertise WhatsApp to boutiques that cannot use it ------

  Follows from issue 1. The Connect plan's feature list contains

      "WhatsApp & Print campaigns"

  and it renders for every boutique, including those whose login response says
  whatsapp_enabled: false.

  Everywhere else in the portal we honour that flag — the Messages tab, the
  campaign channels, the consent dots, the enquiry-number field, the usage
  meter on this same page are all hidden for those boutiques. This list is the
  one thing we cannot hide, because matching on the words "WhatsApp" inside a
  free-text sentence would break the first time the wording or the language
  changes.

  You confirmed the flag is account-level — not a plan tier — so for these
  boutiques the line is not an upsell. It is advertising something no plan
  would give them.

    NEEDED: either leave that feature out of the response when the boutique
    has no WhatsApp entitlement, or send the per-feature key from issue 1 so we
    can filter on something stable. Note the line covers Print as well, which
    they do get — so dropping the whole line loses a real feature. Splitting it
    into two features, or sending a print-only variant, is cleaner.

  For reference, our own copy of this list at /subscription-setup already
  handles it: the line reads "Print campaigns" for a boutique without WhatsApp,
  and Starter's "No WhatsApp" line is dropped entirely.


################################################################################
SUPPORT — QUICK HELP ICON NAMES
################################################################################

  GET /boutique/support/quick-help returns an `icon` per article, and two of
  them rendered on the Support page as words rather than pictures:

      "icon": "menu_book"       showed as   _BOOK
      "icon": "track_changes"   showed as   TRACK_CHANGES

  the second in display type across the whole sidebar.

  Not your bug — the cause is on our side. The portal ships a subset of the
  Material Symbols font (275 icons, 32 KB) rather than the full one, which is
  3.9 MB and never finished downloading. A Material Symbols icon is drawn by
  writing its name as the element's text and letting the font replace it with
  a picture; when the font has no such glyph, nothing replaces the text, so the
  merchant reads the name.

  Both are now in the font, and any name we do not have falls back to a real
  icon instead of printing itself, so this cannot recur visibly.

    USEFUL, NOT BLOCKING: if there is a fixed set of icon names these articles
    can use, send us the list and we will bake all of them in, so a new help
    article always gets its intended icon rather than the fallback. Equally, if
    you would rather not think about it, adding articles freely is fine now —
    an unknown icon simply shows a generic one.

--- 1. The house model images time out, so generation fails -------------------

  On screen, in the portal:

      Failed to load model image: Failed to load image from URL:
      https://apidev.revoltution.com/uploads/ai_studio/models/
      model-default-bella-30f1913e.png
      Error: HTTPSConnectionPool(host='apidev.revoltution.com', port=443):
      Read timed out.

  That is your worker's own message (HTTPSConnectionPool is Python requests),
  not ours — the portal never fetches this file. We measured the URL from
  outside, six times:

      Content-Length:  2,443,261 bytes  (2.4 MB)

      attempt 1   stalled at 179,860 bytes, killed at 60s
      attempt 2   stalled at 179,860 bytes, killed at 20s
      attempt 3   completed 2,443,261 bytes in 14.9s
      attempt 4   completed 2,443,261 bytes in 18.0s
      attempt 5   stalled at 179,860 bytes, killed at 45s
      attempt 6   stalled at 179,860 bytes, killed at 45s

  Headers come back immediately (200, first byte at 1.2s) and nginx declares
  the full 2.4 MB. The transfer then stalls at exactly 179,860 bytes in four
  of six attempts — the same byte count every time, which reads like one
  buffer going out and nothing after it. The two that finished ran at about
  136 KB/s, so even a success takes 15–18 seconds. Any ordinary client
  timeout loses this more often than it wins.

  Three separate things, smallest first:

    1. THE FILE IS 2.4 MB. It is a default house model reference photo. At a
       sane size — a 1024px-wide JPEG or WebP is well under 300 KB — this
       problem mostly disappears on its own, without touching the server.
       Worth checking the other model-default-* files too; if they were all
       uploaded at camera resolution they will all behave this way.

    2. THE STALL ITSELF. Consistently 179,860 bytes suggests nginx sends its
       first buffer and then the upstream or the connection dries up. Worth a
       look at sendfile / proxy_buffering / output_buffers, and at whether
       anything is rate-limiting /uploads/.

    3. THE WORKER FETCHES OVER THE PUBLIC INTERNET. If the Python worker runs
       on the same host as nginx, it is going out to apidev.revoltution.com
       over HTTPS and back in again to read a file that is already on local
       disk. Reading the path directly would make this instant and immune to
       all of the above. If it genuinely runs elsewhere, ignore this one.

  NEEDED: at minimum 1. Ideally 3 as well, which removes the whole class of
  failure rather than making it less likely.

  We have nothing to fix on our side — the portal only displays the message
  your worker returns. If you would rather it did not print the raw Python
  traceback to a boutique, send a short message and we will show that instead.


--- 2. No way to delete a generation --------------------------------------------

  There is no DELETE for a generation. We have:

      GET   /boutique/ai-studio/generations           (list)
      GET   /boutique/ai-studio/generations/:id       (poll)
      POST  /boutique/ai-studio/generations/:id/cancel
      POST  /boutique/ai-studio/generations/:id/regenerate
      POST  /boutique/ai-studio/generations/:id/save-to-gallery
      POST  /boutique/ai-studio/generations/:id/retouch

  cancel only applies to one still running. Nothing removes a finished record,
  so every failed shoot stays on the Hub forever. With issue 1 above failing
  most shoots, the boutique's Recent generations is now mostly failures it has
  no way to clear — and that is the first screen of the feature.

    NEEDED: DELETE /boutique/ai-studio/generations/:id.

  RELATED QUESTION: does a failed shoot cost the boutique a generation from its
  quota? Cancel says it does not ("Cancelled — quota was not charged"), but we
  do not know what a failure does. If failures are charged, the model-image
  timeouts above have been quietly eating a paid allowance, and that needs
  refunding as well as fixing.
